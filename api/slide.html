Programação de Aplicativos • Projeto Cantina • HTML + CSS + JavaScript + PHP + MySQL

Visão geral

Da ficha de papel ao QR Code

🎫

Antes: ficha de papel

A ficha se perde, é copiada, é usada duas vezes. No fim do dia ninguém sabe quantos lanches saíram nem para qual turma.

📱

Agora: QR Code do aluno

Cada aluno tem um QR único. No balcão, o atendente aponta a câmera e o sistema responde na hora: entregue ou não liberado.

📊

E o histórico fica

Toda entrega é gravada com aluno, atendente, dia e hora. A supervisão tira o relatório por dia e por turma.

A regra principal Um lanche por aluno por dia. Quem garante isso não é a tela — é o banco de dados, com UNIQUE (aluno_id, data).

Visão geral

As três camadas do sistema

HTML

Navegador

Telas, CSS e JavaScript. Mostra os dados e coleta o que o usuário digita.

fetch()

Pedido HTTP

O JavaScript pede ou envia dados em JSON, sem recarregar a página.

PHP

API no servidor

Confere login e perfil, valida, aplica as regras e fala com o banco.

MySQL

Banco de dados

Guarda turmas, alunos, usuários e entregas. Garante as regras com chaves.

A ideia central O navegador nunca fala direto com o MySQL. Ele só conversa com a API — e a API decide o que pode.

O que todo arquivo da API reaproveita

api/conexao.php (resumo)header('Content-Type: application/json; charset=utf-8'); function responder($dados, $status = 200) { http_response_code($status); echo json_encode($dados); exit; } $pdo = new PDO('mysql:host=localhost;dbname=cantina', 'root', ''); session_start(); function exigirSupervisor() { if (($_SESSION['usuario']['perfil'] ?? '') !== 'supervisor') { responder(['erro' => 'Acesso permitido só para supervisor.'], 401); } }
Nunca: valor do usuário colado no SQL$pdo->query("DELETE FROM alunos WHERE id = $id"); // $id = "1 OR 1=1" -> apaga TODOS os alunos
Sempre: prepared statement com ?$pdo->prepare('DELETE FROM alunos WHERE id = ?') ->execute([$id]);
Por que isso importa O ? faz o MySQL tratar o valor como dado, nunca como comando. É a defesa contra SQL Injection.

O navegador é do usuário Tudo que vai para o navegador — HTML, CSS, JavaScript e os dados dentro dele — pode ser lido e alterado por quem está usando.
Hoje a senha só existe no banco, como hash (password_hash()), e só o PHP confere (password_verify()).
Por que PHP • 2 de 3

Só JavaScript × JavaScript + API PHP

Tudo no navegador

  • Senhas e dados visíveis no F12
  • Não consegue falar com o MySQL: o navegador só fala HTTP
  • Usuário e senha do banco teriam que ir no código
  • Regras burláveis: o aluno muda o JS e libera 2 lanches
  • Dados só naquele computador (localStorage)
  • Recarregou a página, as alterações somem
VS

Navegador + API PHP

  • Senha do banco fica no servidor, em conexao.php
  • PHP fala com o MySQL pelo PDO
  • Login com sessão: o servidor sabe quem é quem
  • Regras no servidor e no banco: não dá para burlar pelo F12
  • Todos os atendentes veem os mesmos dados
  • Tudo gravado no banco, com histórico
Por que PHP • 3 de 3

Então o JavaScript não valida nada?

🙂

Validação no JavaScript = conforto

Avisa na hora que falta um campo, sem ir ao servidor. Melhora a experiência — mas pode ser desligada por quem sabe abrir o F12.

if (dados.nome === '') mostrarMensagem(...)
🔒

Validação no PHP = segurança

Repete as checagens no servidor, onde o usuário não mexe: campos vazios, perfil válido, matrícula repetida, quem está logado.

if (!in_array($perfil, ['atendente','supervisor']))
E por que PHP, e não Node.js? O ponto é ter um servidor, não a linguagem. Node.js também resolveria. Escolhemos PHP porque o WAMP já traz Apache + PHP + MySQL prontos no laboratório.

Por que não colocar a matrícula no QR? Matrícula é fácil de adivinhar — qualquer um geraria o QR do colega. O código aleatório não dá para inventar.

Quem barra o segundo lanche O UNIQUE (aluno_id, data) da tabela entregas. Mesmo que dois atendentes leiam o mesmo QR no mesmo segundo, o banco aceita só um.
Banco de dados

O modelo por trás de tudo

Uma turma tem N alunos • um aluno retira N lanches (um por dia) • um usuário registra N entregas. Todas as tabelas em InnoDB, para as chaves estrangeiras valerem.
